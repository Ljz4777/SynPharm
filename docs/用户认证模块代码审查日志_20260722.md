## 2. 后端问题清单

### 2.1 🔴 严重问题 (Critical)

#### CRT-B-001：登出接口无需认证即可调用

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 严重 / 安全性 |
| **描述** | `/api/auth/logout` 接口在 SecurityConfig 中被配置为 `permitAll()`，无需认证即可访问。攻击者可以通过暴力枚举Token并调用登出接口，将合法用户的Token加入黑名单，导致合法用户被强制登出。 |
| **位置** | `src/main/java/com/synpharm/config/SecurityConfig.java` |
| **修复建议** | 将 `/api/auth/logout` 从 `permitAll()` 中移除，确保只有已登录用户才能登出自己的Token。 |

---

#### CRT-B-002：验证码生成使用非安全随机数

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 严重 / 安全性 |
| **描述** | `EmailCaptchaServiceImpl.generateCaptcha()` 使用 `java.util.Random` 生成6位数字验证码。`Random` 是伪随机数生成器，种子可预测，攻击者可能通过观察历史验证码预测后续验证码。 |
| **位置** | `src/main/java/com/synpharm/service/impl/EmailCaptchaServiceImpl.java` |
| **修复建议** | 使用 `java.security.SecureRandom` 替代 `Random`，生成不可预测的安全随机验证码。 |

---

#### CRT-B-003：并发注册可能导致数据库异常

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 严重 / 代码正确性 |
| **描述** | `QQEmailLoginStrategy.registerNewUser()` 采用"先查询后插入"的模式（check-then-act）。在并发场景下，两个相同邮箱的并发请求可能同时通过 `user == null` 的检查，然后都尝试插入用户。虽然数据库唯一约束会阻止第二条插入，但会抛出 `DuplicateKeyException`，返回"系统错误"，用户体验差。 |
| **位置** | `src/main/java/com/synpharm/service/strategy/QQEmailLoginStrategy.java` |
| **修复建议** | 在 `QQEmailLoginStrategy` 中捕获 `DuplicateKeyException`，重新查询用户后返回登录成功；或使用分布式锁保证并发安全。 |

---

### 2.2 🟠 主要问题 (Major)

#### MAJ-B-001：登录限流仅基于账号，无IP级限流

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 安全性 |
| **描述** | 登录失败锁定仅基于账号，攻击者可以遍历大量不同的账号进行暴力破解尝试，而不会被锁定IP。验证码发送也仅基于邮箱限制，没有IP级频率限制。 |
| **位置** | `AuthServiceImpl.java`、`EmailCaptchaServiceImpl.java` |
| **修复建议** | 增加IP维度的登录失败计数和锁定机制；增加IP维度的验证码发送频率限制；建议IP+账号双维度限流。 |

---

#### MAJ-B-002：验证码字符串比较存在时序攻击风险

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 安全性 |
| **描述** | `EmailCaptchaServiceImpl.verifyCaptcha()` 使用 `String.equals()` 比较验证码，该方法不是常量时间比较，理论上存在时序攻击（Timing Attack）风险。 |
| **位置** | `EmailCaptchaServiceImpl.java` |
| **修复建议** | 使用 `MessageDigest.isEqual()` 或手动实现常量时间比较。 |

---

#### MAJ-B-003：JWT密钥未做长度校验

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 代码正确性 |
| **描述** | `JwtUtils.getSigningKey()` 直接使用配置的 secret 生成 HMAC 密钥，未校验密钥长度。若配置的密钥过短（少于256位/32字节），`Keys.hmacShaKeyFor()` 会在运行时抛出 `WeakKeyException`。 |
| **位置** | `src/main/java/com/synpharm/utils/JwtUtils.java` |
| **修复建议** | 在 `@PostConstruct` 方法中校验密钥长度，不足则启动时报错；或在配置文件中明确要求密钥至少32字符。 |

---

#### MAJ-B-004：Token黑名单使用完整Token作为Redis Key

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 性能 |
| **描述** | Token黑名单使用完整JWT Token字符串作为Redis Key的一部分。JWT Token通常有数百字符长，会浪费Redis内存。且Token中没有 `jti`（JWT ID）声明。 |
| **位置** | `AuthServiceImpl.java`、`JwtAuthenticationFilter.java`、`JwtUtils.java` |
| **修复建议** | 在JWT中添加 `jti` 声明（UUID），使用jti作为黑名单Key；或对Token做SHA-256哈希后作为Key。 |

---

#### MAJ-B-005：登录限流检查非原子操作

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 代码正确性 |
| **描述** | `AuthServiceImpl.checkLoginLock()` 中先调用 `hasKey()` 再调用 `getExpire()`，两次Redis操作之间存在竞态条件。极端情况下Key可能在两次调用之间过期。 |
| **位置** | `AuthServiceImpl.java` |
| **修复建议** | 使用 Lua 脚本保证原子性；或一次操作同时获取值和过期时间。 |

---

#### MAJ-B-006：X-Forwarded-For 头可伪造

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 安全性 |
| **描述** | `getClientIp()` 方法直接信任 `X-Forwarded-For` 请求头，客户端可以伪造该头来伪造IP地址，导致IP限流、日志记录等功能失效。 |
| **位置** | `AuthServiceImpl.java`、`QQEmailLoginStrategy.java` |
| **修复建议** | 配置可信代理服务器正确设置 X-Forwarded-For；设置受信任的代理IP列表。另外两个类中 `getClientIp()` 方法重复，应抽取为公共工具方法。 |

---

#### MAJ-B-007：DTO验证缺乏条件验证

| 项目 | 内容 |
| :--- | :--- |
| **分类** | 主要 / 可维护性 |
| **描述** | `LoginRequest` DTO 中字段使用 `@Pattern` 注解，但没有根据 `loginType` 进行分组验证。例如当 `loginType` 为 `qq_email` 时，`email` 和 `captcha` 应该是必填的，但当前传空也能通过校验（@Pattern对null值返回true）。 |
| **位置** | `src/main/java/com/synpharm/dto/request/LoginRequest.java` |
| **修复建议** | 使用 Spring Validation 的分组验证功能实现条件验证；或使用自定义校验注解实现跨字段条件校验。 |

### 2.3 🟡 次要问题 (Minor)

#### MIN-B-001：getClientIp 方法重复实现

- **描述**：`AuthServiceImpl` 和 `QQEmailLoginStrategy` 中各有一份完全相同的 `getClientIp()` 方法，代码重复。
- **位置**：`AuthServiceImpl.java`、`QQEmailLoginStrategy.java`
- **修复建议**：抽取到公共工具类（如 `IpUtils`）中统一维护。

#### MIN-B-002：getAccount 返回 "unknown" 兜底值不合理

- **描述**：无法获取账号时返回字符串 `"unknown"`，会导致 "unknown" 这个"账号"被锁定。
- **位置**：`AuthServiceImpl.java`
- **修复建议**：当无法获取账号时，直接抛出 `BAD_REQUEST` 业务异常。

#### MIN-B-003：JWT Token 多次重复解析

- **描述**：`JwtAuthenticationFilter` 中同一个Token被解析了3次（validateToken、getUserIdFromToken、getRoleFromToken），造成不必要的性能损耗。
- **位置**：`JwtAuthenticationFilter.java`、`JwtUtils.java`
- **修复建议**：添加一个方法一次解析返回包含用户信息的DTO。

#### MIN-B-004：JWT签名密钥每次调用都重新创建

- **描述**：`JwtUtils.getSigningKey()` 每次调用都重新生成 `SecretKey` 对象，密钥是固定的，应缓存。
- **位置**：`JwtUtils.java`
- **修复建议**：使用 `@PostConstruct` 初始化时一次性创建并缓存 `SecretKey`。

#### MIN-B-005：错误码设计不统一

- **描述**：`ErrorCode` 枚举中混用了HTTP状态码（200、400等）和自定义业务错误码（1001、2001等），语义不清晰。
- **位置**：`ErrorCode.java`、`GlobalExceptionHandler.java`
- **修复建议**：业务错误码统一使用自定义编码规则；HTTP状态码和业务错误码分离。

#### MIN-B-006：登出时Token为null直接返回无提示

- **描述**：`AuthServiceImpl.logout()` 中，token为null或空直接静默返回，调用方不知道是否成功。
- **位置**：`AuthServiceImpl.java`
- **修复建议**：Token为空时抛出异常或返回明确提示。

#### MIN-B-007：验证码发送频率限制检查非原子

- **描述**：`EmailCaptchaServiceImpl.checkSendLimit()` 使用 `get()` + `parseInt()` 的方式检查，存在竞态条件，且 `NumberFormatException` 未被捕获。
- **位置**：`EmailCaptchaServiceImpl.java`
- **修复建议**：使用 `increment()` 原子操作后再判断是否超限。

## 4. 重点问题深度分析

### 4.1 前端 validatePassword 函数名冲突（最高优先级）

**问题描述**：
Login.vue 中导入了 `validatePassword`，又定义了同名的局部函数，导致递归调用栈溢出。

```typescript
// 从 validators 导入
import { validateQqEmail, validatePassword } from '@/utils/validators'

// 局部函数（与导入函数同名，会遮蔽导入的函数）
const validatePassword = (): boolean => {
  const result = validatePassword(password.value)  // ← 这里调用的是自身，导致无限递归
  errors.password = result.valid ? '' : result.message
  return result.valid
}
```

**影响**：登录功能完全失效，调用后页面卡死/崩溃。

**修复方案**：重命名局部函数为 `validatePasswordField`（与 Register.vue 一致）。

---

### 4.2 登出接口无需认证（安全风险）

**问题描述**：
`/api/auth/logout` 在 SecurityConfig 中被配置为 `permitAll()`，任何人都可以调用。

**风险**：
虽然 JWT Token 本身很难被暴力枚举，但：
1. 如果攻击者通过其他方式获取了 Token（如XSS），可以直接让用户失效
2. 设计上不符合最小权限原则

**修复方案**：从 permitAll 列表中移除 logout 路径。

---

### 4.3 并发注册问题（竞态条件）

**问题描述**：
```java
// QQEmailLoginStrategy.login() 中
SysUser user = userMapper.selectByEmail(email);
if (user == null) {
    user = registerNewUser(email);  // 并发时两个线程都可能走到这里
}
```

**风险**：
- 高并发下可能抛出 `DuplicateKeyException`
- 全局异常处理会返回"系统错误"，用户体验差

**修复方案**：
捕获 `DuplicateKeyException`，异常后重新查询用户并返回登录成功（幂等设计）。

---

### 4.4 验证码安全随机数问题

**问题描述**：
使用 `java.util.Random` 生成验证码，该类不是密码学安全的。

**风险**：
理论上攻击者可以通过多次请求观察验证码规律，预测后续验证码。

**修复方案**：
```java
// 替换前
Random random = new Random();
String code = String.format("%06d", random.nextInt(1000000));

// 替换后
SecureRandom secureRandom = new SecureRandom();
String code = String.format("%06d", secureRandom.nextInt(1000000));
```
