# SynPharm 上线流程（Go-Live Runbook）

> 版本：v1.0
> 更新日期：2026-08-07
> 适用范围：从当前"可本地运行"状态推进到"对外提供生产服务"
> 前置阅读：`docs/deploy/容器化部署与Docker环境指南.md`、`docs/deploy/部署指南.md`

本流程将上线拆为 **9 个阶段**，每个阶段包含目标、具体步骤、验收标准。请逐项执行并打勾，任何阶段未通过验收不进入下一阶段。

```
阶段0 前置决策 → 阶段1 代码整改 → 阶段2 测试补齐 → 阶段3 CI/CD
     → 阶段4 服务器环境 → 阶段5 生产部署 → 阶段6 运维保障
     → 阶段7 验收切换 → 阶段8 正式上线运营
```

---

## 阶段 0：上线前置决策

**目标：** 确定上线所需的资源与责任归属，避免中途改方案。

| # | 决策项 | 说明 | 建议 |
|---|---|---|---|
| 0.1 | 服务器 | 云厂商 + 规格 + 地域；是否需要 GPU（FastAPI 推理 `DEVICE=cuda:0`） | CPU 入门 2C4G 可跑，正式对外建议 4C8G；AI 推理量大再上 GPU 机型 |
| 0.2 | 域名 | 绑定前端的正式域名 | 国内服务器域名需 **ICP 备案**（约 1~3 周），务必提前 |
| 0.3 | 镜像仓库 | 镜像推送/拉取源 | Docker Hub / 阿里云 ACR / 腾讯云 TCR / Harbor |
| 0.4 | 数据库 | 沿用容器 MySQL 或云数据库（RDS） | 正式环境建议云 RDS（自带备份/高可用） |
| 0.5 | 负责人 | 明确各阶段 owner 与审批人 | - |
| 0.6 | 版本号 | 本次上线发布版本 | 建议 `v1.0.0` 打 Git tag |

**验收：** 服务器、域名（含备案状态）、镜像仓库、数据库方案均已确定，形成部署环境登记表。

## 阶段 1：代码整改（阻断级缺口）

**目标：** 修复上表中标记为"阻断级"的问题，确保功能真实可用、无安全后门。

### 1.1 移除调试后门接口
- 删除 `synpharm-backend/src/main/java/com/synpharm/api/AuthController.java` 中的 `@PostMapping("/debug/login")`（含 `debugLogin` 方法）。
- 删除前端 `synpharm-frontend/src/api/auth.ts` 中的 `debugLogin` 方法及其调用点。
- 同步删除相关文档中的后门说明，避免误导。

### 1.2 前端接入真实 API（去 Mock）
当前 `Predict.vue` / `Dashboard.vue` / `Results.vue` / `Tasks.vue` / `Profile.vue` / `Targets.vue` 无条件使用 `src/data/mockResults.ts`，生产构建也显示假数据。需：
- 将这些页面改用 `src/api/*.ts`（`auth.ts` / `predict.ts`）请求真实后端。
- 删除或条件编译 mock 引用（仅保留在 `VITE_ENABLE_MOCK=true` 的开发场景）。
- 补齐"保存结果""3D 可视化"等按钮的真实功能，或上线前明确标注为"即将上线"并禁用。

### 1.3 邮件服务配置
- 在 `deploy/.env` 配置 `QQ_EMAIL` 与 `QQ_EMAIL_AUTH_CODE`（QQ 邮箱 → 设置 → 账户 → 开启 SMTP 并获取授权码）。
- 未配置前验证码无法发送，注册/登录不可用，属阻断项。

### 1.4 AI 模型文件就位
- 将训练好的 DTI / PPI / DDI 模型权重放入 `synpharm-fastapi/models/`（卷挂载，不入镜像）。
- 用一条真实样本（如文档中的 SMILES/序列）在 FastAPI `/v1/predict/single` 验证三类型都能返回结果。

### 1.5 生产配置加固
修改 `synpharm-backend/src/main/resources/application-docker.yml`：
- `knife4j.enable: false`（生产关闭 API 文档，仅内网/测试开启）。
- `logging.level.com.synpharm: info`；`mybatis-plus` 的 `log-impl` 改为 `org.apache.ibatis.logging.nologging.NoLoggingImpl`（避免 SQL/敏感日志）。
- `management.endpoint.health.show-details` 生产改为 `when-authorized`。
- 确认 `jwt.secret` 走环境变量 `JWT_SECRET`（已有 fail-fast）。

**验收：**
- `debug/login` 全库检索无残留。
- 前端 `npm run build` 后无 mock 数据引用（或仅存在于受控开关后）。
- 三类型预测各跑通一次并落库。
- 注册→收验证码→登录→预测→查结果 全链路可用。

## 阶段 3：CI/CD 与镜像仓库

**目标：** push 代码即可自动构建、测试、推送镜像，消除"本地构建版本漂移"。

1. 初始化 Git 远程仓库（GitHub / Gitee / GitLab），`git remote add origin <url>`。
2. 配置镜像仓库凭据（GitHub Actions Secrets：`REGISTRY`、`REGISTRY_USERNAME`、`REGISTRY_PASSWORD` 或云厂商 Token）。
3. 新建 `.github/workflows/ci.yml`，流程：
   - **触发**：`push` 到 `main` + 打 `v*` tag。
   - **后端**：`mvn test` → 失败即停。
   - **前端**：`npm ci && npm run build`。
   - **FastAPI**：`pytest`。
   - **镜像**：构建 `synpharm/backend|frontend|fastapi:<tag>` 并推送到仓库。
   - **部署（可选）**：SSH 到服务器 `docker compose pull && docker compose up -d`。
4. 本地也可 `docker compose build` 后 `docker tag` + `docker push` 手动发布。

**验收：** push 触发流水线全绿，镜像在仓库中可 `docker pull`。

## 阶段 4：服务器环境准备

| # | 步骤 | 说明 |
|---|---|---|
| 4.1 | 开通云服务器 | 规格按 0.1；系统 Ubuntu 22.04 / Debian 12 |
| 4.2 | 安装 Docker + Compose | `curl -fsSL https://get.docker.com \| sh`；验证 `docker version`、`docker compose version` |
| 4.3 | 安全组/防火墙 | 仅放行：`80`/`443`（HTTP/HTTPS）、`22`（SSH，建议改端口+密钥登录）；**不放行** `3306`/`6379`/`8080`/`8000` 到公网 |
| 4.4 | 域名解析 | 添加 A 记录：`synpharm.example.com → 服务器公网 IP` |
| 4.5 | 数据盘（可选） | 挂载并让 Docker 数据卷落盘（`/var/lib/docker`） |
| 4.6 | 时区/字符集 | `timedatectl set-timezone Asia/Shanghai`；`LANG=C.UTF-8` |

**验收：** 公网 `curl -I http://<IP>` 能连通（阶段 5 部署后 80 有响应）。

## 阶段 5：生产部署

### 5.1 拉取代码并准备配置
```bash
cd /opt && git clone <repo> SynPharm && cd SynPharm/deploy
cp .env.example .env
```

### 5.2 生产 .env 关键项
```ini
SYNPHARM_VERSION=v1.0.0
MYSQL_ROOT_PASSWORD=<openssl rand -base64 18>
MYSQL_PASSWORD=<openssl rand -base64 18>
REDIS_PASSWORD=<强密码>
JWT_SECRET=<openssl rand -hex 32>
FASTAPI_API_KEY=<openssl rand -hex 32>      # 开启算法引擎认证
FASTAPI_API_KEYS=<同上>
QQ_EMAIL=your@qq.com
QQ_EMAIL_AUTH_CODE=<授权码>
FRONTEND_PORT=80
BACKEND_PORT=8080
FASTAPI_PORT=8000
```
> ⚠️ `deploy/.env` 已被 `.gitignore` 忽略，勿提交；仅在服务器上创建。

### 5.3 启动
```bash
./scripts/start.sh        # 或 docker compose up -d --build
docker compose ps         # 期望全部 healthy
```

### 5.4 部署后冒烟验收
```bash
curl http://localhost/                     # 前端 200
curl http://localhost:8080/actuator/health # {"status":"UP"}
curl http://localhost:8000/health          # healthy
# 带 X-API-Key 调一次预测验证认证生效
```

### 5.5 HTTPS（必须）
- 方案 A（推荐）：云负载均衡/Nginx 托管证书。
- 方案 B：Certbot 自动签发：
  ```bash
  docker run -it --rm -p 80:80 -v certbot:/etc/letsencrypt \
    certbot/certbot certonly --standalone -d synpharm.example.com
  ```
  将证书挂载到前端 nginx，`nginx.conf` 增加 `listen 443 ssl` + 80→443 跳转，并把 `/api/` 反代改为 `X-Forwarded-Proto https`。

**验收：** `https://synpharm.example.com` 可访问、浏览器无安全告警、登录/预测全链路通过。

## 阶段 6：运维保障（监控/日志/备份）

| # | 项目 | 落地方式 |
|---|---|---|
| 6.1 | 资源限制 | 在 `docker-compose.yml` 为各服务加 `deploy.resources.limits`（CPU/内存），防单服务拖垮宿主机 |
| 6.2 | 进程监控 | UptimeRobot / 云监控，对 `https://synpharm.example.com`、`/actuator/health` 定时探测并告警 |
| 6.3 | 指标监控 | 后端接入 `micrometer-registry-prometheus` 暴露 `/actuator/prometheus`，配 Prometheus + Grafana |
| 6.4 | 日志 | 至少 `docker compose logs -f` 排障；规模变大再上 Loki/ELK 集中收集 |
| 6.5 | 数据库备份 | 定时任务：`mysqldump` 每日全量 + binlog 增量，存异地（云 OSS/对象存储）；**每月恢复演练一次** |
| 6.6 | 上传/结果目录 | 确认 `backend_uploads`/`backend_results` 卷纳入备份 |
| 6.7 | 配置备份 | `deploy/.env`、nginx 配置、compose 文件纳入版本库（.env 用示例占位） |

**验收：** 断网/杀进程/停 MySQL 场景能自动恢复（`restart: unless-stopped` 已配）；备份文件可成功还原到空库。

## 阶段 7：验收与上线切换

### 7.1 功能验收清单
- [ ] 注册 → 邮箱验证码 → 登录 → 退出
- [ ] 三类型预测（DTI/PPI/DDI）单条与批量（CSV 上传）
- [ ] 任务进度查询、结果下载
- [ ] 收藏/个人中心
- [ ] 移动端/不同浏览器兼容
- [ ] 弱网/大文件上传（100MB）表现

### 7.2 性能压测
- 用 wrk / k6 / JMeter 对登录、单条预测、批量预测做并发测试，记录 P95 延迟与吞吐。
- 依据结果确定是否需要扩容/加队列。

### 7.3 切换与回滚
- 若已有旧版本：域名解析/负载均衡做灰度切量（先 10% → 50% → 100%）。
- **回滚预案**：保留上一版镜像 tag；异常时 `docker compose down && 切回旧 tag up`，或 DNS 切回旧地址。目标回滚时间 < 30 分钟。

**验收：** 功能验收全过、压测数据记录在案、回滚演练成功至少一次。

## 阶段 8：正式上线运营

1. **最终上线检查单**（见附录）全部打勾。
2. **切换 DNS/负载均衡**到生产，宣布上线。
3. **首周灰度观察**：监控错误率、延迟、资源水位，每日 Review 日志。
4. **建立迭代机制**：
   - 每版本打 tag → CI 自动发版。
   - 维护 `CHANGELOG.md`（已有）。
   - 版本升级时同步更新 `SYNPHARM_VERSION`。
5. **应急预案**：将排障步骤（`docker compose logs`、重启、回滚）整理成 Runbook 并培训到人。

**验收：** 稳定运行 ≥ 1 周无 P0 故障，迭代流程跑通。
